# 数据库并发控制深度解析：从 MVCC 到可串行化

## 1. 核心概念：MVCC 与快照隔离

### 1.1 MVCC（多版本并发控制）

MVCC 是 PostgreSQL 实现并发控制的核心机制。其核心思想是：**读操作不阻塞写操作，写操作不阻塞读操作**。

PostgreSQL 通过为每一行数据维护多个版本来实现这一点。每个数据行包含以下隐藏字段：
- `xmin`：创建该版本的事务 ID
- `xmax`：删除该版本的事务 ID（初始为 0）
- `cmin`/`cmax`：命令 ID（用于同一事务内的可见性判断）

当一个事务读取数据时，它会根据当前事务 ID 和快照（Snapshot）判断哪些版本是可见的。快照记录了事务开始时的活跃事务列表，从而确定一个"时间点"，所有在该时间点之前提交的数据版本对该事务可见。

### 1.2 快照隔离（Snapshot Isolation, SI）

PostgreSQL 的默认隔离级别是 **READ COMMITTED**，其底层实现基于 MVCC，提供的是**快照隔离**语义。

在快照隔离下：
- 每个事务看到的是一个**一致的数据库快照**，即事务开始时刻（对于 READ COMMITTED，是每条语句开始时刻）已提交的数据状态。
- 事务内的所有读操作都基于这个快照，不会看到其他事务在快照之后提交的修改。
- 写操作会检查冲突：如果两个事务修改同一行，后提交的事务会检测到冲突并回滚（在 READ COMMITTED 下，后提交事务会看到最新值并重新执行；在 REPEATABLE READ 下，会直接报错）。

**关键特性**：快照隔离保证每个事务看到的数据是一致的，但**不保证事务之间的执行顺序等价于某个串行顺序**。

## 2. 写偏差（Write Skew）：一个具体的时序示例

写偏差是快照隔离下特有的异常现象，它发生在两个事务读取相同数据，然后基于各自读取的值进行写操作，导致最终结果违反业务不变量。

### 2.1 场景设定

假设有一个医院系统，要求**至少有一名医生处于值班状态**。数据库表 `doctors` 包含字段 `id` 和 `on_call`（布尔值）。

初始状态：
- 医生 A：`on_call = true`
- 医生 B：`on_call = true`

业务不变量：**`COUNT(on_call = true) >= 1`**

### 2.2 事务时序

| 时间 | 事务 T1（医生 A 下班） | 事务 T2（医生 B 下班） |
|------|------------------------|------------------------|
| t1   | `BEGIN;`               |                        |
| t2   |                        | `BEGIN;`               |
| t3   | `SELECT count(*) FROM doctors WHERE on_call = true;`<br>结果：2 |                        |
| t4   |                        | `SELECT count(*) FROM doctors WHERE on_call = true;`<br>结果：2 |
| t5   | `UPDATE doctors SET on_call = false WHERE id = 'A';` |                        |
| t6   |                        | `UPDATE doctors SET on_call = false WHERE id = 'B';` |
| t7   | `COMMIT;`              |                        |
| t8   |                        | `COMMIT;`              |

### 2.3 结果分析

- T1 在 t3 读取时，看到 2 名医生值班，满足不变量，因此允许 A 下班。
- T2 在 t4 读取时，由于快照隔离，T2 看到的仍然是 t2 时刻的快照（T1 尚未提交），因此也看到 2 名医生值班，允许 B 下班。
- 两个事务都成功提交后，数据库中 `on_call = true` 的医生数量为 **0**，**违反了业务不变量**。

这就是写偏差：两个事务各自基于一致快照做出决策，但组合起来破坏了全局约束。

### 2.4 为什么快照隔离无法防止写偏差？

快照隔离保证每个事务内部的一致性视图，但不保证事务之间的**写-写冲突检测**覆盖所有业务逻辑。T1 和 T2 修改的是**不同的行**（A 和 B），因此 PostgreSQL 的 MVCC 冲突检测机制（基于行锁）不会检测到冲突。

## 3. 可串行化隔离（Serializable Isolation）

PostgreSQL 的 `SERIALIZABLE` 隔离级别通过 **SSI（Serializable Snapshot Isolation）** 算法实现，它在快照隔离的基础上增加了**冲突检测**，确保事务的执行结果
